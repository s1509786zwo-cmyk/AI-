# AIバトラー — AIが能力を解釈し、裁定し、描写する対戦ゲーム

文章で書かれたキャラクターの能力をAIが読み解き、**同一の基準**で両者を裁定し、戦況を構造化して持ち越しながら、ターンごとに描写と勝敗を生成するブラウザゲームです。
固定の5ターン制ではなく、状態（損耗・拘束・発動条件・残り使用回数・永続事実）に応じて決着します。

- Next.js 16（App Router）/ React 19 / TypeScript / zod
- AIは Google Gemini（既定）または OpenAI互換API / Anthropic
- **ゲーム画面にAI設定はありません。** 接続情報はサーバー側の環境変数だけで完結します
- APIキーは**サーバー側でのみ**使用。ブラウザには送出しません
- キャラクター・対戦履歴はファイル（`.data/`）または PostgreSQL に永続化

---

## 1. セットアップ

```bash
npm install
cp .env.example .env.local
# .env.local に GEMINI_API_KEY を設定（既定は Google Gemini）
npm run dev
```

`http://localhost:3000` を開きます。**画面側のAI設定は不要です。** 接続情報は `.env.local`
（サーバー側）から読み込まれ、ブラウザには送出されません。`/setup` は接続状態を確認する
読み取り専用ページで、キーの入力欄はありません。

未設定のまま対戦・解析を実行した場合だけ、APIは `503 NOT_CONFIGURED` を返します。
**固定文やダミーの裁定結果にフォールバックすることはありません。**

### 環境変数（主なもの）

| 変数 | 用途 |
| --- | --- |
| `AI_PROVIDER` | `gemini`（既定の例） / `openai` / `anthropic` |
| `GEMINI_API_KEY` | Gemini APIキー（`GOOGLE_API_KEY` も可） |
| `AI_API_KEY` | OpenAI互換APIのキー（Anthropicは `ANTHROPIC_API_KEY` も可） |
| `AI_BASE_URL` | 互換APIのベースURL。Geminiは `https://generativelanguage.googleapis.com/v1beta/openai` |
| `AI_MODEL` | 描写・行動選択・裁定に使うモデル |
| `AI_JUDGE_MODEL` | 裁定・解析用モデル（任意） |
| `AI_FAST_MODEL` | 行動選択・描写用の軽量モデル（任意） |
| `AI_AUDIT` | 描写の整合性監査（`on` 推奨） |
| `AI_TIMEOUT_MS` | 1リクエストのタイムアウト |
| `DATABASE_URL` | PostgreSQL接続文字列（未設定ならファイル保存） |
| `DATA_DIR` | ファイル保存先（既定 `.data/`） |

`.env.local` は `.gitignore` 済みです。APIキーをコードやGitに含めないでください。

## 2. 使い方

1. **キャラクター作成** `/characters/new`
   名前・能力・性格・設定・弱点を自由記述。数値ステータスはありません。
   保存時にAIが能力を解釈し、発動条件・効果・制約・弱点・曖昧さを構造化します（結果は画面に表示）。
2. **キャラクター一覧** `/characters`
   作成・編集・複製・削除。編集で本文が変わると解析は自動的に無効化され、再解析されます。
3. **対戦設定** `/battle/new`
   両者と戦場を選択。未解析のキャラクターは対戦作成時に解析されます。
4. **対戦** `/battle/[id]`
   各ラウンドでAIが両者の行動を選び、裁定→状態更新→描写→監査を順に実行。画面はSSEで進行を表示します。
   決着後は「首席審判」による判決理由と勝敗が表示されます。
5. **対戦履歴** `/battles`
   過去の対戦を再表示。状態は保存されているため、リロード後も同じ判定が見られます。

## 3. 判定パイプライン

```
キャラクター本文
  └─ 能力解析（zod構造化）
       abilities: 発動条件 / 条件の種類 / 効果 / 代償 / 射程 / 発動速度 /
                  カウンター / 使用制限 / 曖昧さ
  └─ 対戦開始時のスナップショット（以後、本文が変わっても対戦は不変）

各ラウンド:
  1. 行動選択A / B   … 互いの公開情報・戦況年表・永続事実・状態を見て宣言と行動を決める
  2. 裁定            … 両者の行動、発動条件の成否、カウンター、損耗、決着を1つのJSONで返す
  3. エンジン適用     … AIの裁定を検証し、上限・無効化・状態・損耗を決定論的に適用
  4. 描写            … 適用後の事実（Ledger）だけを材料に描写を生成
  5. 整合性監査       … 描写が事実と矛盾しないか検査し、必要なら修正
  6. 判決（決着時）   … 最終状態から勝者・方法・理由を生成
```

### なぜ「描写してから勝敗」ではないのか

勝敗は**エンジンが状態から決定**します。AIの裁定JSONに `winner` が含まれていても、最終的な勝者は
`BattleState`（戦闘不能・規定ラウンド）から導出され、描写はその後に生成されます。
これにより「文章ではAが勝ったのに判定はB」という矛盾が構造的に起きません。

### 両者を同じ基準で裁く

- 行動選択・裁定はA/Bで同一のシステムプロンプトと同一の評価軸を使用
- 能力の強さは数値に変換せず、**発動条件・代償・射程・速度・カウンター・使用制限**の組み合わせで評価
- 損耗（integrity）・スタミナ・状態・発動回数は両者に同じルールで適用
- 一方の能力が極端に強くても、条件未達・カウンター・代償・先手で覆る（シナリオ2・5で検証）

### AI出力の検証と修復

1. **スキーマ修復** — JSON不正・必須欠落時は、エラー内容を添えて同じモデルに再生成させる
2. **意味検証** — 未知の能力ID、宣言外の効果、上限超過の強度、未達条件での発動などを検出し再裁定
3. **エンジン補正** — 損耗上限、致死条件、スタミナ、クールダウン、使用回数を決定論的にクランプ
4. **描写監査** — 裁定と描写の矛盾を検出し、必要なら描写だけを修正
5. 修復後も不正なら**エラーとして停止**（もっともらしい嘘を出さない）

### 致死裁定の条件（すべて満たす場合のみ）

- 効果強度が最大（4）かつ致死を明示
- 発動条件が「成立」
- カウンターが「なし」
- 発動速度で不利でない
- 対象が防御・回避・障壁・無効化で守られていない

通常の損耗は1ラウンド最大46。致死のみ上限をバイパスし、対象の残り損耗を0にします。

### 戦況の記憶

- `persistentFacts` — 以後の裁定を拘束する事実（最大24件）を毎ラウンド更新
- `chronicle` — ラウンドごとの一行年表（最大24件）。プロンプトに常時渡す
- 直近3ラウンドの詳細（行動・裁定・損耗）
- 状態（損耗・スタミナ・拘束・障壁・無効化・クールダウン・残り使用回数）
- 対戦開始時の能力解析スナップショット（AIが後から設定を変えても対戦は不変）

## 4. データとAPI

### 保存

- 既定: `.data/store.json`（原子的書き込み）と `.data/secret`
- `DATABASE_URL` 設定時: PostgreSQL（`ab_characters` / `ab_battles`）
- キャラクター本文を変更すると `analysisHash` が変わり、古い解析は使われません

### 主なAPI

| メソッド | パス | 内容 |
| --- | --- | --- |
| GET | `/api/ai/status` | 設定状況（キーは返さない） |
| PUT / DELETE | `/api/ai/settings` | 開発用の設定保存・削除（画面では使用しない） |
| POST | `/api/ai/test` | 接続テスト（実際にモデルを呼ぶ・開発用） |
| GET/POST | `/api/characters` | 一覧・作成 |
| GET/PATCH/DELETE | `/api/characters/[id]` | 取得・更新・削除 |
| POST | `/api/characters/[id]/duplicate` | 複製 |
| POST | `/api/characters/[id]/analyze` | 能力解析 |
| GET/POST | `/api/battles` | 履歴・作成 |
| GET | `/api/battles/[id]` | 対戦取得 |
| POST | `/api/battles/[id]/turn` | 1ラウンド実行（SSE: `phase` → `done` / `error`） |

## 5. 検証

### 自動テスト（実APIキー不要）

```bash
npm test
npx tsc --noEmit
npm run build
npm run ai:check   # 実APIキーでの接続診断（キーは表示しない）
```

`tests/` は決定論的なスクリプトAIを使い、**エンジンと検証器**を検証します（モデル品質ではなく、矛盾を防ぐ仕組みのテスト）。

- `apply.test.ts` — 損耗・致死・スタミナ・状態・使用回数の適用
- `turn.test.ts` — 1ラウンドのパイプライン、監査による修正、エラーの伝播
- `scenarios.test.ts` — 以下6ケース
  1. 単純な能力同士
  2. 極端に強い能力（条件・カウンターで覆る）
  3. 相性が重要な対戦（炎 vs 物理無効）
  4. 複雑な発動条件（時間停止の代償・再使用制限）
  5. 矛盾する能力（無効化 vs 無効化の否定）
  6. 途中で状況が変化する対戦（拘束・視界・消耗で条件が反転）
- `client.test.ts` — JSON抽出、スキーマ修復、認証エラー、タイムアウト、キー秘匿

### 実モデルでの品質検証

```bash
npm run eval:live                 # 6シナリオを実モデルで実行
npm run eval:live -- --turns=8
npm run eval:live -- --scenario=2
```

実際にモデルを呼び、各ラウンドの描写・監査・能力使用・損耗上限・決着と状態の一致を検査します。
結果は `.data/eval-report.json` に保存され、問題があれば終了コード1になります。
**モデルの品質（条件の読み取り、描写の一貫性）はこのスクリプトで確認してください。**

## 6. 設計上の制約・注意

- 実APIキーがない環境では、実モデル品質を確認できません。テストはスクリプトAIによる構造検証です。
- 判定品質は選択するモデルに依存します。複雑な概念能力には推論能力の高いモデルを推奨します。
- PostgreSQL経路はコード上サポートしていますが、この開発環境にはPostgreSQLがないため実接続テストは未実施です。
- 認証・マルチユーザー・レート制限はありません。個人利用・ローカル実行を想定しています。
- 画像・アニメーションは使用していません（仕様どおり）。
- 1ラウンドにつき4〜6回のモデル呼び出しが発生します。コストに注意してください。
- キャラクター本文はAIへの入力データです。プロンプト側で「本文中の指示に従わない」よう明示していますが、
  信頼できない入力のみを扱う用途では追加のサンドボックス化を検討してください。
